# CL0.1 results: rank-5 FNO cost

3D CL0.1 (`docs/laplace3d/tasks/CL0.1.md`), measured 2026-11-24 on the Mac and 2026-11-25 on
the VM (cuda). Code: `spikes/fno3d_cost/` (non-default workspace member). The cuda run
confirms batch 20 at s = 64 (D4).

## Machines and method

- **Mac:** Apple M2 Pro, 16 GB unified memory, macOS 26.6.2, rustc 1.99.0, release
  profile, Burn 0.23.0-pre.2 (the pin), commit `f3bc90d`. One run at a time.
- **VM:** 2× A100 80 GB, GPU 0 only, nothing else running on it; Burn 0.23.0-pre.2, commit
  `4a90772`, 2026-11-25 10:35–10:52 UTC, started by the coordinating session at the
  author's go (log `~/sciml-rs/logs/cl0-1.log` on the VM). Full 1000/200 epochs, no
  extrapolation.
- `fno3d_cost <s> <modes> <batch> <n_train> <n_test>` builds the real training components
  (`build_training_components::<5, 4, f32>`: `FNO<5>`, width 32, 4 layers, `modes` per
  axis, one data channel; Adam with weight decay; cosine schedule) on synthetic data
  `[N, s, s, s, 1]`, runs epoch 0 as a warm-up (kernel compilation, autotune) and reports
  epoch 1: `train_epoch` plus `evaluate`, each read back to the host, so a GPU is
  synchronised when the clock stops. **Time per epoch** is that epoch's per-sample times
  scaled to 1000 train and 200 test samples (D5's split). On the Mac N is small (40/20 at
  s = 32 on metal, 8/4 or 4/2 on flex and at s = 64), so these are extrapolations; the VM
  runs full 1000/200 epochs.
- **Peak memory**, read outside the process by `spikes/fno3d_cost/run.sh`: macOS
  `/usr/bin/time -l` "peak memory footprint" (whole process, whole lifetime); cuda the
  process's largest `nvidia-smi` reading every 200 ms (the caching allocator's
  reservation, CUDA context included).
- **Activation memory per sample** is the slope of peak memory between two batch sizes at
  the same N, so the resident data, the model and Adam's state cancel.

## Time per epoch (1000 train + 200 test samples)

| s | modes | flex (Mac) | metal (Mac) | cuda (A100) |
| --- | --- | --- | --- | --- |
| 32 | 8³ | 550–592 s (b 2, 4) | 58–60 s (b 4, 8, 20) | 21.7 s (b 10), **11.1 s (b 20)** |
| 32 | 12³ | 607–656 s (b 2, 4) | 60–66 s (b 4, 8, 20) | 22.1 s (b 10), **11.4 s (b 20)** |
| 64 | 8³ | 2956–3181 s (b 1, 2) | 378–387 s (b 1, 2, 4) | 64.2 s (b 10), 63.4 s (b 20) |
| 64 | 12³ | 3044–3282 s (b 1, 2) | 388–419 s (b 1, 2, 4) | 65.1 s (b 10), **64.0 s (b 20)** |

- Time barely depends on the modes (at most 11 %, flex at s = 32) or the batch: the FFTs and pointwise layers
  on s³ points dominate, not the spectral weights.
- s = 64 costs 6.4× s = 32 on metal and 5× on flex, for 8× the points.
- 500 epochs (the 2D Phase 5 length) on metal: about 8 h at s = 32, about 55 h at s = 64.
  For comparison, 2D at s = 64 on cuda is 1.7 s per epoch.
- On cuda (epoch 1; epoch 0, with autotune, took 23–150 s): s = 32 is overhead-bound (batch
  20 halves the epoch against batch 10), s = 64 compute-bound (about 64 s whatever the
  batch or the modes). 500 epochs at batch 20: about **1.6 h at s = 32 and 8.9 h at
  s = 64**, 6× faster than metal at s = 64.

| --- | --- | --- | --- | --- |
| 32 | about 0.25 GB | 0.08 (8³), 0.15 (12³) GB | about 0.10 GB (12³, b 4 → 20) | 0.13 (8³), 0.17 (12³) GB |

| 64, batch 20 | about 35–40 GB | about 23 GB of activations (20 × slope) | – | peak 30.6 GB in all (12³) |

- **flex is the clean reading**: host memory, no autotune. Its s = 64 slope, 1.15–1.19 GB
  per sample, is about 26–43 % under §7's estimate; s = 32 is about an eighth of it (0.15 GB,
  modes 12³; the 8³ pair, 0.08 GB, is the noisier two-point slope).
- **metal's footprint is noisy and is not used for the decision.** Runs whose warm-up
  epoch was slow (autotune: 48–63 s against 7–8 s) read 1–2.6 GB higher (metal s = 32,
  8³, b 8 and b 20; s = 64, 8³, b 1 is above b 2), and Burn's fusion may keep fewer
  intermediates than flex. The metal slopes are about half of flex's.
- At s = 64, batch 20, flex's slope gives about 23 GB of activations, plus the train split
  on the device (2.1 GB), the model and Adam (≤ 1 GB): about 26 GB, a third of an A100
  80 GB. The cuda run confirms it: **30.6 GB peak at s = 64, modes 12³, batch 20** (`nvidia-smi`,
  the caching allocator's reservation, CUDA context included), 29,146 of the A100's 81,920 MiB (36 %). The
  cuda slope at s = 64 is 0.84 GB (8³) and 1.44 GB (12³) per sample, read from the
  allocator's reservation at b 10 and 20 with N = 1000.
- On the 16 GB Mac, metal ran s = 64 up to batch 4 (3.8 GB footprint); batch 20 at s = 64
  does not fit there on the flex slope.

## zip64 round trip

On the Mac (APFS), `zip64_roundtrip` wrote f and u `[1000, 65, 65, 65]` f64 with the
writer `write_split` uses (`ndarray_npy::NpzWriter::new`, stored, zip 6.0.0) into one
file of **4 394 000 526 bytes (4.09 GiB, above 4 GiB)** in 4.0 s, read both back with
`NpzFileReader` in 4.2 s (output in `spikes/fno3d_cost/mac.log`, last section), and **every value matched bit for bit**.
On the VM (Linux) the same check wrote 4 394 000 526 bytes in 1.9 s and read f and u back
bit for bit in 1.4 s (2026-11-25). Peak memory 2.2 GB (one
field at a time).

- So a 3D n = 65 train split fits one `.npz` as written today: zip 6 writes the zip64 end
  of central directory and offsets by itself once the archive passes 4 GiB.
- The limit is per member: zip 6 refuses a single member above 4 GiB unless the member's
  `large_file` option is set (`zip-6.0.0/src/write.rs`, "Large file option has not been
  set"), and `NpzWriter::new` does not set it. At n = 65 in f64 one field is
  2.197 GB per 1000 samples, so a member passes 4 GiB at 1955 samples; D5's 1000/200 and a
  200-sample n = 129 test split (3.43 GB per field) stay under it. Not run: reading the
  file with NumPy. The VM's file system passes too (above).

## D4 (signed off by the author 2026-11-25, as proposed here)

**Width 32, 4 layers, modes 12³ at s = 32 and s = 64; batch 20 at both s.** The cuda run
confirms batch 20 at s = 64: 30.6 GB peak, and the same time per epoch as 8³ (64 s).

Evidence: 12³ fits (56.6 M parameters, under 1 GB with Adam), costs at most 11 % more time
than 8³, and keeps the 2D rule (modes min(12, s/2), Phase 5), so 2D and 3D compare at the
same modes. Memory is set by the activations, not the modes: about 26 GB at s = 64,
batch 20 on the flex slope, inside one A100 80 GB. Alternative: modes 8³ (16.8 M
parameters), if the author prefers fewer parameters per training sample (56.6 M weights for
1000 samples is 24× the 2D model); it saves no memory and little time.

## D5 (signed off by the author 2026-11-24, as proposed here)

**n = 33 (tests and Mac runs) and n = 65 (training); n = 129 a test-only set only if the
resolution study needs it; 1000 train / 200 test; names `poisson3d_n{n}_K{K}_{split}`;
f64 storage, one `.npz` per split as in 2D, no file split.**

Evidence: the zip64 round trip above (4.09 GiB, bit for bit, the writer and reader as they
are). f32 storage would halve the files (n = 65 train 2.2 GB) but loses the labels' f64
precision, which the transfer floor (error 2) is measured against; f64 costs nothing in
code. Host memory to load n = 65 (two f64 fields, 4.4 GB, plus the transferred copies)
stays a VM job (D8), as §7 says.

## The cuda run (VM, 2026-11-25)

Run as planned (`docs/laplace3d/tasks/CL0.1.md`): `cargo build --release -p fno3d-cost-spike
--features cuda`, then `zip64_roundtrip` and `run.sh cuda` with `cuda.cfg` on GPU 0, s = 32
and 64, modes 8³ and 12³, batch 10 and 20, full 1000/200 epochs. 17.5 min in all (10:35–
10:52 UTC), every configuration exit 0. Results in the tables above; the log is on the VM
(`~/sciml-rs/logs/cl0-1.log`).

## Reproduction (Mac)

```sh
cargo test -p fno3d-cost-spike                        # parameter counts against §7
cargo build --release -p fno3d-cost-spike --features metal
cp target/release/fno3d_cost /tmp/fno3d_cost_metal    # BURN_DEVICE picks metal or flex
bash spikes/fno3d_cost/run.sh metal /tmp/fno3d_cost_metal < spikes/fno3d_cost/metal.cfg
bash spikes/fno3d_cost/run.sh flex  /tmp/fno3d_cost_metal < spikes/fno3d_cost/flex.cfg
target/release/zip64_roundtrip /tmp/zip64.npz         # 4.4 GB of free disk
```

About 45 minutes for the matrix. `spikes/fno3d_cost/mac.log` is its output verbatim, with the zip64 run's output appended.
