## 5. Measured numbers against the proposal

| §7 quantity | §7 estimate | Measured (CL0.1) | Against §7 |
| --- | --- | --- | --- |
| Parameters, modes 12³ / 8³ | 56 631 841 / 16 785 953 | same, exact | equal |
| Activations per sample, s = 32 | about 0.25 GB | 0.15 GB flex, 0.17 GB cuda (12³) | 30–40 % under |
| Activations per sample, s = 64 | about 1.6–2 GB | 1.15–1.19 GB flex, 1.44 GB cuda (12³) | 10–43 % under |
| Batch 20, s = 32 | about 5 GB | 5.87 GB peak cuda (12³), all in | about 17 % over |
| Batch 20, s = 64 | about 35–40 GB | 30.6 GB peak cuda (12³), all in; 36 % of an A100 | 13–24 % under |
| Time per epoch, 1000 + 200, batch 20, 12³ | not estimated | cuda 11.4 s (s = 32), 64.0 s (s = 64); metal 60–66 s, 388–419 s | new |
| 500 epochs, batch 20, 12³ | – | cuda about 1.6 h (s = 32), 8.9 h (s = 64); metal about 8 h, 55 h | new |
| Storage, n = 65, 1000 train, f + u, f64 | 5.3 GB for 1200 | 4.39 GB file for 1000 (same rate) | equal |
| zip64 (R6) | "CL0.1 checks it, or split the file" | one `.npz` of 4.09 GiB round-trips bit for bit on the Mac and the VM, writer and reader unchanged | no split needed |

Corrections they imply:

- §7's activation estimate scaled the 2D measurement by the 64× point count; the measured
  slope is lower at s = 64 (and at batch 20, s = 32, the total is 17 % above it, the fixed
  costs counting more there). The estimate is
  conservative and safe to keep as a bound, but the measured column should replace it as
  the figure of record (C1).
- Time, not memory, is the constraint: s = 64 is compute-bound on cuda (64 s per epoch
  whatever the batch or the modes) and s = 32 overhead-bound (batch 10 → 20 halves it). Modes
  cost at most 11 % more time. R1's mitigations (modes 8³, a smaller batch, factorised
  weights) are not needed at width 32; D4 already took 12³.
- The zip64 limit is per member, not per file: `NpzWriter::new` does not set zip's
  `large_file`, so one field above 4 GiB fails, which at n = 65 in f64 is 1955 samples. D5's
  1000/200 and a 200-sample n = 129 test split stay under it; a larger n = 65 split would
  need `large_file` or two files (C2).
- The Mac's 16 GB runs s = 64 only up to batch 4 on metal, and 500 epochs at s = 32 on
  metal take about 8 h against 1.6 h on one A100 (Q1, D8).

## 9. Retrospective on the loop

- **The VM run held the milestone open.** CL0.1's PR waited a day for its cuda run (as the
  L1 gate said, the critical path). Planning a VM run at the task's start, and starting it
  as soon as the spike builds, would have closed L0 a day earlier. `/next-task` could put a
  task's VM steps first in its plan when the task has *Machines: the VM*.
- **Review verdicts not recorded.** CL0.1's progress entry says "Review: see the PR", and
  the PR text has no review section; the verdict (thermo-nuclear APPROVE) exists only in
  the git-ignored report. `/next-task`'s log step should require the verdict in the
  progress entry, as CL0.2's has.
- **A spike's memory reading needs a clean backend.** metal's footprint was noisy enough
  to be set aside; reading flex (host, no autotune) and cuda (allocator reservation) gave
  consistent slopes. Spikes that measure memory should name the backend used for the
  decision in their plan.
- What worked: measuring against D5's real split size (1000/200) on the VM rather than
  extrapolating, and testing parameter counts against §7 exactly, made both decisions quick
  to sign off.
